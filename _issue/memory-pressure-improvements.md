# Задача: доработка freeing_up_memory для более безопасной работы при давлении на память

## Контекст

Утилита `freeing_up_memory` используется на ноутбуке с 16 GB RAM для предотвращения зависаний рабочего окружения при одновременной работе тяжелых приложений: GoLand, браузеры, Telegram и другие GUI-программы.

До появления утилиты при нехватке памяти система могла становиться практически неуправляемой: переставала двигаться мышь, невозможно было закрыть приложения, рабочий стол зависал. Текущая утилита решает эту практическую проблему как аварийный защитный механизм.

Отключать `freeing_up_memory` не нужно. Требуется доработать ее так, чтобы сохранить защитную функцию, но уменьшить риск лишней очистки cache, лишнего I/O и нежелательного совпадения очистки с suspend/resume.

## Текущее поведение

Сейчас утилита раз в минуту проверяет свободную память и при `Free < 1 GB` выполняет очистку page cache:

```bash
sync && echo 3 | sudo tee /proc/sys/vm/drop_caches
```

Ключевые места в коде:

- `/home/shmel/go/src/freeing_up_memory/internal/memory/memory.go:10` - порог `1 GB`
- `/home/shmel/go/src/freeing_up_memory/internal/memory/memory.go` - получение памяти через `gopsutil/mem`
- `/home/shmel/go/src/freeing_up_memory/internal/systray/sistray.go` - периодическая проверка раз в минуту

Текущий подход смотрит на `Free`, а не на `Available`. В Linux значение `Free` может быть низким из-за page cache, хотя эта память может быть освобождена ядром при необходимости. Из-за этого утилита может запускать `drop_caches` раньше, чем начинается реальная нехватка памяти.

## Связанная диагностика системы

По системным логам проблема с черным экраном после lock/suspend выглядит как отдельная проблема NVIDIA/GSP timeout, а не как прямое следствие работы `freeing_up_memory`.

При этом перед ошибками NVIDIA в логах наблюдалось давление на память и срабатывание очистки cache. Поэтому утилиту нужно не отключать, а сделать более аккуратной и наблюдаемой.

На системе также был добавлен `zram`:

- `/dev/zram0` около `7.6 GB`
- алгоритм `zstd`
- priority `100`
- обычный `/swapfile` `8 GB` остался резервным swap с priority `-2`

Новая логика должна учитывать, что при пиках памяти первым должен использоваться быстрый `zram`, а `drop_caches` должен оставаться аварийной мерой.

## Цель

Сохранить способность утилиты предотвращать жесткие зависания рабочего стола при нехватке памяти, но сделать срабатывание очистки cache более осознанным, настраиваемым и безопасным.

## Не цели

- Не отключать сервис `freeing_up_memory`.
- Не удалять `drop_caches` полностью.
- Не заменять утилиту на другой memory manager.
- Не менять настройки NVIDIA, suspend/resume или zram в рамках этой задачи.
- Не делать сложный GUI-конфигуратор, если достаточно конфигурационного файла.

## Функциональные требования

### 1. Использовать более полную метрику памяти

Добавить сбор и логирование следующих значений:

- `Free`
- `Available`
- `Used`
- `Total`
- `SwapTotal`
- `SwapUsed`
- `SwapFree`
- процент использования RAM
- процент использования swap

Рассмотреть изменение условия срабатывания с:

```text
Free < 1 GB
```

на более устойчивую логику, например:

```text
Available < 1.5-2 GB
```

или комбинированное условие:

```text
Available < configured_threshold AND SwapUsed is growing
```

Итоговая формула должна быть вынесена в отдельную функцию, чтобы ее можно было тестировать.

### 2. Добавить cooldown между очистками cache

Утилита не должна выполнять `drop_caches` слишком часто.

Требуется добавить минимальный интервал между очистками, например `5-10 минут`.

Поведение:

- если память ниже порога, но cooldown еще не истек, очистку не выполнять;
- записать в лог, что очистка пропущена из-за cooldown;
- в tray-иконке продолжать отображать актуальное состояние памяти.

Параметр cooldown должен быть настраиваемым.

### 3. Добавить подробное логирование перед очисткой

Перед каждым выполнением `drop_caches` нужно логировать snapshot состояния памяти.

Минимальный набор данных в логе:

```text
memory pressure detected:
total=...
free=...
available=...
used=...
swap_total=...
swap_used=...
swap_free=...
threshold=...
cooldown=...
last_cleanup_at=...
action=drop_caches
```

После очистки нужно повторно считать память и залогировать результат:

```text
cache cleanup completed:
free_before=...
free_after=...
available_before=...
available_after=...
duration=...
```

При ошибке выполнения команды очистки лог должен содержать саму ошибку и команду, которая не выполнилась.

### 4. Не выполнять очистку рядом с suspend/resume

Добавить защиту от запуска `sync` и `drop_caches` в момент, когда система уходит в сон или только что проснулась.

Возможные варианты реализации нужно исследовать отдельно:

- проверять systemd/logind состояние;
- слушать D-Bus signal `PrepareForSleep`;
- использовать lock-файл или timestamp, который выставляется systemd sleep hook;
- добавить отдельный systemd hook, который временно блокирует очистку на время suspend/resume.

Минимальное желаемое поведение:

- перед suspend очистка cache не запускается;
- сразу после resume есть grace period, например `1-2 минуты`;
- если очистка пропущена из-за sleep state или grace period, это пишется в лог.

### 5. Сделать настройки конфигурируемыми

Жестко заданные значения нужно вынести в конфиг.

Параметры:

- интервал проверки памяти, сейчас `60s`;
- порог `Available`, например `2 GB`;
- порог `Free`, если он остается частью формулы;
- cooldown между очистками;
- grace period после resume;
- включение/отключение фактического `drop_caches`;
- dry-run режим для тестирования;
- путь к `/proc/sys/vm/drop_caches`.

Предпочтительный простой формат:

- `/etc/freeing_up_memory/config.toml`

или пользовательский конфиг:

- `$HOME/.config/freeing_up_memory/config.toml`

Нужно определить приоритет конфигов и значения по умолчанию.

### 6. Убрать зависимость от `sudo tee`, если сервис уже имеет нужные права

Сейчас команда выглядит так:

```bash
sync && echo 3 | sudo tee /proc/sys/vm/drop_caches
```

Нужно оценить текущую модель запуска:

- сервис запущен от пользователя `shmel`;
- для записи в `/proc/sys/vm/drop_caches` используется `sudo`;
- GUI/tray требует пользовательскую сессию и `DISPLAY=:0`.

Нужно предложить безопасную архитектуру:

- оставить tray-приложение от пользователя, а очистку выполнять через отдельный root-helper;
- или оставить текущую схему с `sudo`, но явно описать требования к sudoers;
- или разделить приложение на user tray и system service.

Важно: решение не должно ломать текущий сценарий, где утилита уже работает и помогает.

### 7. Добавить режим наблюдения без очистки

Нужен `dry-run` режим, при котором утилита:

- считает память;
- принимает решение, что очистка была бы нужна;
- пишет это в лог;
- не выполняет `sync` и `drop_caches`.

Это нужно для безопасной проверки новых порогов.

### 8. Улучшить отображение состояния в tray

Сейчас в tray отображается число свободной памяти.

Нужно рассмотреть более информативный формат:

- показывать `Available`, а не `Free`;
- возможно отображать `A:9.5` или просто `9.5`;
- tooltip должен показывать полный snapshot: Free, Available, Used, SwapUsed;
- при cooldown или memory pressure можно менять цвет/icon state.

GUI-часть не должна быть обязательной для работы логики.

## Нефункциональные требования

- Утилита должна оставаться легкой по CPU и RAM.
- Проверка памяти не должна сама создавать заметную нагрузку.
- Очистка cache не должна запускаться чаще заданного cooldown.
- Логика принятия решения должна быть покрыта unit-тестами.
- Код должен быть разделен так, чтобы memory policy можно было тестировать без system tray и без реального `/proc/sys/vm/drop_caches`.
- Ошибки очистки не должны приводить к падению процесса.
- При отсутствии GUI/tray логика мониторинга должна иметь возможность работать в headless-режиме, если это будет выбрано в спецификации.

## Предлагаемая структура доработки

Возможные новые компоненты:

- `internal/memory` - сбор snapshot памяти;
- `internal/policy` - принятие решения о необходимости cleanup;
- `internal/cleanup` - выполнение `sync` и `drop_caches`;
- `internal/config` - чтение настроек;
- `internal/sleep` - определение suspend/resume state или grace period;
- `internal/systray` - только отображение состояния и меню.

## Критерии приемки

Задача считается выполненной, если:

1. Утилита продолжает запускаться как раньше и не требует отключения сервиса.
2. Порог срабатывания больше не завязан только на `Free < 1 GB` без учета `Available`.
3. Между реальными очистками cache есть настраиваемый cooldown.
4. Перед каждой очисткой и после нее пишется подробный лог memory snapshot.
5. Есть защита от очистки непосредственно перед suspend и сразу после resume либо явно описанный технический способ ее реализации.
6. Основные параметры вынесены в конфиг или подготовлены к конфигурированию.
7. Есть dry-run режим.
8. Логика принятия решения покрыта unit-тестами.
9. Сервис не выполняет `drop_caches` чаще, чем разрешено cooldown.
10. При ошибке очистки cache процесс не падает, а пишет понятный лог.

## Сценарии тестирования

### Нормальная нагрузка

Условие:

- `Available` существенно выше порога;
- swap не используется или используется минимально.

Ожидаемый результат:

- очистка не выполняется;
- tray показывает актуальное состояние;
- лог не засоряется лишними сообщениями.

### Давление на память

Условие:

- `Available` ниже порога;
- возможно начал использоваться zram.

Ожидаемый результат:

- утилита пишет memory snapshot;
- выполняет очистку cache, если cooldown истек;
- после очистки пишет результат.

### Cooldown активен

Условие:

- память ниже порога;
- предыдущая очистка была недавно.

Ожидаемый результат:

- очистка не выполняется;
- в лог пишется причина `cooldown active`.

### Dry-run

Условие:

- память ниже порога;
- включен dry-run.

Ожидаемый результат:

- команда `drop_caches` не выполняется;
- в лог пишется, что очистка была бы выполнена.

### Suspend/resume

Условие:

- система уходит в сон или только что вышла из сна.

Ожидаемый результат:

- очистка cache не запускается в опасный момент;
- после grace period утилита возвращается к штатной логике.

## Открытые вопросы для будущей спецификации

1. Какой порог `Available` выбрать по умолчанию для 16 GB RAM: `1.5 GB`, `2 GB` или другой?
2. Нужно ли учитывать `SwapUsed`, особенно после добавления zram?
3. Какой cooldown выбрать по умолчанию: `5 минут` или `10 минут`?
4. Нужно ли разделять GUI/tray и root cleanup helper на два процесса?
5. Как лучше интегрироваться с systemd sleep: D-Bus, hook или простой grace period после resume?
6. Нужно ли оставлять `Free` в tray, или заменить отображение на `Available`?
7. Требуется ли headless-режим без tray для запуска как чистый system service?

## Риски

- Слишком высокий порог может приводить к частой и ненужной очистке page cache.
- Слишком низкий порог может не успевать предотвращать desktop-freeze.
- Частый `sync` может вызывать I/O-паузы.
- Некорректная интеграция с suspend/resume может совпасть с проблемами NVIDIA-драйвера и усложнить диагностику.
- Разделение на user GUI и root helper усложнит установку и поддержку.

## Ожидаемый результат разработки

После доработки `freeing_up_memory` должна оставаться практической защитой от зависаний при нехватке памяти, но работать более предсказуемо:

- меньше ложных срабатываний;
- понятные логи;
- настраиваемые пороги;
- защита от слишком частой очистки;
- совместимость с текущей схемой zram + swapfile;
- меньший риск вмешательства в suspend/resume.
